# RTX 2060 measurements

Measured on 2026-10-30 on one NVIDIA GeForce RTX 2060 (6 GB, compute capability 7.5). Driver 595.79. PyTorch 2.15.0+cu132. TF32 was off. CUDA times are medians of CUDA events and include Python launch overhead. They are not Nsight kernel times.

Official FlashAttention-2 did not run. `flash_attn` is not installed, and this GPU is Turing (7.5). The project refuses that backend below compute capability 8.0. The CUDA decode numbers below are the repository kernel in `cuda/decode_attention.cu`: FP32, one query, online softmax over a KV cache. That kernel is not FlashAttention-2.

Correctness against the PyTorch reference stayed around 1e-7 absolute error for the streaming and decode comparisons.

## Convolution

3×3, stride 1, padding 1, FP32. Five warmup iterations, 20 timed iterations. CSV: `benchmark_conv.csv`.

| Shape (N, Cin, H, W, Cout) | cuDNN ms | Explicit im2col ms | CUDA implicit GEMM ms | im2col extra alloc | implicit extra alloc |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1, 1, 16, 16, 16 | 0.078 | 0.272 | 0.165 | 8.15 MB | 0.03 MB |
| 4, 1, 32, 32, 16 | 0.078 | 0.223 | 0.166 | 8.52 MB | 0.50 MB |
| 2, 16, 16, 16, 32 | 0.081 | 0.196 | 0.203 | 8.47 MB | 0.17 MB |
| 2, 16, 32, 32, 32 | 0.075 | 0.180 | 0.224 | 9.50 MB | 0.64 MB |

Implicit GEMM is 2.1–3.0× slower than cuDNN on every shape. It is faster than explicit im2col only on the two smallest shapes, and it allocates far less than the unfold buffer.

## Does the decode kernel help?

One new query, FP32, 4 heads, head dimension 32. Five warmup iterations, 20 timed iterations. Compared with materialized `QK^T` and with PyTorch SDPA. Full-sequence FlashAttention-2 rows are absent.

Batch 16 (64 warps):

| KV length | Explicit ms | SDPA ms | CUDA decode ms | Decode vs SDPA |
| --- | ---: | ---: | ---: | ---: |
| 16 | 0.308 | 0.196 | 0.076 | 2.6× faster |
| 64 | 0.266 | 0.139 | 0.097 | 1.4× faster |
| 128 | 0.264 | 0.158 | 0.104 | 1.5× faster |
| 256 | 0.341 | 0.259 | 0.131 | 2.0× faster |
| 1024 | 0.256 | 0.670 | 0.383 | 1.7× faster |

Batch 1:

| KV length | Explicit ms | SDPA ms | CUDA decode ms |
| --- | ---: | ---: | ---: |
| 16 | 0.274 | 0.123 | 0.079 |
| 256 | 0.266 | 0.139 | 0.129 |
| 1024 | 0.344 | 0.324 | 0.332 |

The decode kernel helps against SDPA when the batch is wide enough to occupy warps. At batch 1 and KV length 1024 it does not: one warp per head scans the cache serially. A single GEMM can still beat that scan at long context even when the GEMM writes the score vector.

On a full sequence the custom kernel is not a prefill kernel, so it was not timed. At batch 16 and length 2048, PyTorch SDPA took 3.71 ms and explicit attention took 34.7 ms.

## KV cache at 32×32

Batch 2, random weights, frames from 16 to the model maximum of 256. One warmup pass, three timed passes. Recompute encodes the whole prefix again at every step. The cache encodes only the new frame.

| Frames | Recompute ms | KV cache + SDPA ms | KV cache + CUDA decode ms |
| --- | ---: | ---: | ---: |
| 16 | 31.4 | 33.5 | 25.5 |
| 32 | 56.0 | 58.8 | 54.1 |
| 64 | 120.0 | 119.5 | 117.6 |
| 128 | 232.3 | 235.1 | 225.5 |
| 256 | 503.0 | 474.0 | 452.9 |

At 256 frames, CUDA cache is 1.11× the recompute path (453 ms versus 503 ms). SDPA cache is 1.06×. Shorter clips do not pay for the SDPA cache. The 32×32 encoder is cheap, so repeating old frames is not expensive yet. Logits match recompute within about 2e-7.

Per new frame, attention alone at 16 frames was 0.251 ms explicit, 0.188 ms SDPA, and 0.137 ms CUDA decode. That gap is smaller than the CNN once the clip is short.

## Frame size

Same model and the same 128-d token. Only the input side length changes. Adaptive average pooling still emits a 4×4 grid. Fixed workload: 64 frames, batch 2. One warmup pass, two timed passes. The encoder's 32×32 check was bypassed for this sweep only. The synthetic generator is still calibrated at 32×32.

| Side | Recompute ms | KV + SDPA ms | KV + CUDA decode ms | CUDA vs recompute | Peak GB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 32 | 122 | 123 | 127 | 0.96× | 0.02 |
| 48 | 118 | 134 | 146 | 0.81× | 0.03 |
| 64 | 123 | 125 | 116 | 1.06× | 0.06 |
| 96 | 184 | 125 | 110 | 1.66× | 0.13 |
| 128 | 286 | 134 | 115 | 2.50× | 0.23 |
| 160 | 452 | 166 | 141 | 3.21× | 0.36 |
| 192 | 2815 | 122 | 126 | 22× | 0.52 |
| 256 | 8863 | 149 | 132 | 67× | 0.92 |
| 320 | 4791 | 125 | 112 | 43× | 1.44 |
| 384 | 3396 | 124 | 106 | 32× | 2.08 |
| 512 | 9862 | 181 | 175 | 56× | 3.69 |

Cache time stays near 110–180 ms. Recompute is flat through 64, then climbs smoothly through 160.

**128×128 is the size to report.** It is the first point that is both clearly faster (2.5×, 115 ms versus 286 ms) and still on the smooth part of the curve. Peak memory is 0.23 GB. **160×160** is the last smooth point, at 3.2×.

Sizes from 192 upward are not a good headline. Recompute time jumps by seconds and is not monotonic (256 is slower than 320 and 384). That is cuDNN's algorithm choice on the long prefix, not a larger attention effect. The decode-versus-SDPA gap stays on the order of 20 ms, because the token width does not change with the image side.
